# 專案太多與久未接觸後的接續工作：功能研究

- 研究日期：2026-10-20
- 分支：`feat/project-resume-workspace`
- 狀態：原始研究紀錄。後續已實作聚焦清單、快速收工與接續卡；實際交付與測試結果見 [第一版驗證紀錄](PROJECT-RESUMPTION-VERIFICATION.md)。以下保留研究階段的提案與取捨。
- 方法：檢視現有程式、資料模型與測試，參考原始研究摘要及產品官方文件。

## 1. 結論

**建議先做「少數專案聚焦 → 收工留下一步 → 回來直接接續」的完整流程，不再增加一套待辦系統。**

兩個痛點其實不同：

| 痛點 | 回來時真正需要回答的問題 | 需要補強的能力 |
| --- | --- | --- |
| 專案太多 | 今天到底選哪一個？哪些可以放心先不看？ | 個人聚焦清單、稍後檢視、保留篩選 |
| 太久沒碰 | 這個專案在做什麼？上次停在哪？現在第一步做什麼？ | 簡短收工紀錄、醒目的接續卡、紀錄時間與來源 |

HelpTool 已有狀態、優先級、任務、專案記憶、下一步及接續概覽。真正的缺口不是欄位不足，而是**需要維護的資訊太分散、收工記錄成本高，以及缺少個人注意力管理**。

第一版不必依賴模型 API、讀取聊天紀錄或 IDE 外掛。先用既有資料與明確的人工紀錄，確認這個流程真的能降低重新上手的成本。

## 2. 現有功能與缺口

| 面向 | 已經有 | 本次值得補的部分 |
| --- | --- | --- |
| 整理專案 | 分類、搜尋、狀態篩選、優先度、排序；進行中／暫停／規劃中／已完成／封存 | 個人聚焦／置頂、持久化視圖；不要把「我今天不看」當作專案被暫停 |
| 選擇下一件事 | 首頁最多四項、附理由的規則式推薦 | 使用者明確選定且順序穩定的少數專案；與推薦候選分開 |
| 回到專案 | 概覽已有 checkpoint、下一步、阻礙、任務及 Git 事實 | 將「上次人工留下的狀態＋下一個具體動作」放到最醒目的位置 |
| 記錄脈絡 | 九個記憶欄位、修訂版本、未儲存保護、AI 交接匯回預覽 | 一個不用維護整份筆記的收工入口；後續再加歷史 |
| 任務 | 跨專案搜尋、todo／doing／blocked／done、優先級 | 不另建一份待辦；讓接續卡使用既有任務與 `nextAction` |
| 活動訊號 | 最近 commit、分支、工作目錄變更、記憶更新時間 | 區分「看過」「啟動過」「明確留下 checkpoint」「Git 提交」 |
| 重新整理舊專案 | 可以手動找到暫停專案並修改狀態 | 獨立的待檢視清單，而不是把所有舊專案塞回今日推薦 |

### 關鍵限制

1. 現有 `activityAt()` 只取最後 commit；沒有 commit 的專案不會因此被判為久未活動。這不能解讀成「最近還有在做」。
2. `Project.updatedAt` 是資料更新，不等於實際工作時間；任務也有自己的時間戳。
3. 現有 checkpoint 顯示主要取 `memory.status → notes → overview`，不是歷次工作紀錄。
4. Git 快照只含目前狀態與有限筆數的近期 commit，不能直接宣稱知道「你離開後所有變更」。
5. 開啟 VS Code／外部工具只能知道啟動請求結果，無法得知使用者後續是否工作、做了多久或完成什麼。

## 3. 外部方案帶來的啟發

| 來源 | 原始功能／研究發現 | 適合借用的部分 | 不直接照搬的部分 |
| --- | --- | --- | --- |
| Things 官方工作流程 [S1] | 不近期投入的專案放 Someday，也可用未來日期重新考慮；定期回顧 | 把「現在承諾要做」與「保留但目前不做」分開 | 不必把 HelpTool 變成完整日程／GTD 工具 |
| Linear 專案更新 [S2] | 最新更新放在概覽，歷史另列；health 與生命週期不同 | 每個專案有一份容易找到的最新交接紀錄 | 不加入團隊週報、強制回報及多重健康分數 |
| Eclipse Mylyn [S3] | 依 IDE 互動建立 task context，切換任務時關閉／重開相關編輯器 | 「回到工作」應帶回相關脈絡，而不只是開資料夾 | 單靠 Git 做不到完整 IDE／終端／聊天工作階段恢復 |
| Parnin、DeLine，CHI 2010 [S4] | 問卷與實驗指出，程式工作接續可受益於自動活動線索；實驗中使用者偏好時間序列程式片段 | 人工留下意圖，系統補上可查證的活動事實 | 不把特定實驗的成功率結果宣稱成 HelpTool 的速度提升或長期效果 |

**綜合推論：人工紀錄負責「當時想做什麼」，系統資料負責「現在可觀察到什麼」。兩者互補，不能互相冒充。**

研究限制：上述程式中斷研究不是對本產品的測試，也不能直接證明隔幾個月回來仍有相同比例的改善；需要用真實專案驗證。

## 4. 建議第一版：三個功能形成閉環

### A.「我的聚焦」：今天不必面對全部專案

- 工作台優先顯示使用者選定的少數專案，預設建議三個，可調整，不設硬性上限。
- 聚焦順序由使用者決定，避免每次刷新因推薦分數而跳動。
- 保留明確的「全部專案」入口與既有搜尋；解除聚焦不刪除、不封存、不更改專案狀態。
- 既有推薦保留為候選，不冒充使用者已承諾的工作。
- 聚焦選擇跨重新啟動保留；個人選擇預設留在本機。
- 第一版只需要單一聚焦清單，不先做多套看板、多層標籤和複雜自訂視圖。

**解決：每次打開都要重新從大量專案做選擇。**

「三個」是可驗證的產品預設，不是研究證明的最佳數字。

### B.「收工記一下」：約 30 秒留下可接續的線索

在專案概覽提供明確按鈕，顯示三個問題：

1. 這次停在哪裡？
2. 有什麼卡住或要注意的？（可留空）
3. 下次第一步要做什麼？

設計原則：

- 最少只需確認下一步；其他欄位選填。30 秒是待驗證的體驗目標，不是既有測量結果。
- 預填目前紀錄，只更新使用者提交的欄位；不要求重填九個記憶欄位。
- 重用 `memory.status`、`memory.blockers` 與 `Project.nextAction`，不再新增第四種「下一步」文字。
- 下一步鼓勵具體到可以執行，例如「打開登入測試，重現 token 過期後沒有返回登入頁」，而不是「繼續做登入」。
- 儲存時記錄明確的 checkpoint 時間；不把「最近看過」當成工作完成。
- 保存需要沿用 revision 衝突保護，相關欄位與 checkpoint 標記一併成功或一併失敗。
- 明示這些既有欄位的分享範圍：啟用專案分享後 `nextAction` 會進入共享投影，部分記憶欄位也可能已被選為共享。
- 不在每次切換頁面時強制彈窗、不阻止使用者離開、不監控工時。

**解決：當下知道自己做到哪裡，但過幾週只剩模糊印象。**

第一版只維護最新紀錄，不承諾歷史還原；歷次 checkpoint 是獨立後續功能。

### C.「回來工作卡」：先回答怎麼開始，再呈現細節

升級既有專案概覽，不另外新增一個需要維護的頁面。顯示順序：

1. 專案目的：取既有概述，讓久未接觸時知道為什麼做。
2. 上次留下的狀態及保存日期。
3. 下一個具體動作；未填時提供補寫入口，不捏造建議。
4. 阻礙或待確認事項。
5. 現況：分支、未提交變更、未完成任務及 Git 觀測時間。
6. 既有開啟 IDE／資料夾／複製交接內容操作。

示例，內容為假設資料：

```text
付款工具                         [加入聚焦]
目的：讓小型商戶能追蹤收款狀態

上次紀錄：2026-09-28
停在：退款 API 已接好，尚未測試重複退款
下次第一步：打開 refund.test.ts，補「同訂單第二次退款」測試
注意：測試帳號權限還沒確認

目前 Git：feature/refund · 3 個未提交檔案
觀測於：2026-10-20 20:00（不是最後工作時間）

[開啟 VS Code] [複製交接內容] [收工記一下]
```

舊專案沒有新 checkpoint 時：仍顯示既有記憶，但標成「既有記憶／最後儲存時間」，不能倒填一個不存在的收工紀錄。沒有 Git、路徑失效、刷新失敗都必須保留可讀紀錄，明確標示未知／舊快照。

**解決：資料雖然都在，卻要重新閱讀整份 README、任務和 commit 才能動手。**

## 5. 後續功能與取捨

| 優先順序 | 功能 | 價值／相對成本 | 推進條件 |
| --- | --- | --- | --- |
| P0 | 聚焦清單＋快速收工＋接續卡 | 直接覆蓋兩個痛點；中等範圍 | 先做完整小閉環 |
| P1 | 待檢視清單／稍後再看 | 找回被遺忘的專案，又不增加首頁噪音；小至中 | 確認使用者需要回顧而非更多提醒 |
| P1 | checkpoint 歷史 | 回看過去方向及決策；中 | 當最新一筆不足以理解長期專案 |
| P1 | 保留篩選／批次整理 | 降低大量專案的整理成本；小至中 | 實際清單使用證明需要；封存與刪除分開 |
| P2 | 從上次 checkpoint 到現在的變化 | 比單純近期 commit 更有用；中至大 | 先保存 baseline，處理切分支／rebase／歷史不可達 |
| P2 | 可選摘要草稿／下一步建議 | 減少閱讀成本；資料品質與隱私成本較高 | 先有可靠 checkpoint 和來源；需預覽確認 |
| 暫緩 | 完整 IDE／終端／聊天工作階段恢復 | 潛在價值高，但跨工具整合成本高 | 有明確需求再加 adapter，不能承諾單靠 Git 完成 |

成本為相對工程範圍，不是工期承諾。

### 待檢視清單應與今日工作分開

可收納：使用者設定的檢視日期已到、缺少下一步、很久沒有明確 checkpoint、需要重新確認的暫停專案。

每筆只需選「繼續／稍後再看／封存」。不要因沒有 commit 自動封存，不把「稍後再看」顯示成逾期工作，也不發送每日催促通知。首次上線的未知日期要獨立處理，避免一次把所有舊專案標成過期。

### 建議資料方向，實作前再定案

- 新增本機個人狀態附屬表，保存聚焦順序與明確 checkpoint 時間；P1 才加檢視／稍後再看時間。
- 目前 schema 為 v4；如新增持久化表，走下一版正式 migration，而不是只加 TypeScript 欄位。
- 不為單純查看、聚焦、取消聚焦或 Git polling 增加 `Project.revision`；真正修改記憶／下一步仍須走既有 revision 保護。
- 舊資料中的新時間欄位保持 `null`，不從 commit 或 `updatedAt` 猜成實際工作時間。
- 個人聚焦／稍後再看不進現有共享投影。個人顯示偏好與團隊可見的專案狀態不是同一件事。
- 若後續加入 checkpoint 歷史，另建歷史表；不可宣稱既有 revision 已保存歷次內容。
- 本機專案與共享工作區摘要不是相同物件；遠端專案不能直接開啟本地 IDE，身份也不能只靠 projectId。

### 效能與自動化

- 清單先用已有快取計算，不為每張卡額外呼叫 Git details／diff。
- 目前 paused／completed 專案仍可能參與 Git polling；聚焦或稍後再看若只影響 UI，就不能宣稱會減少背景掃描。
- 不新增全磁碟掃描、不讀私人聊天、不自動執行專案命令、不自動 checkout／stash／commit。
- 如增加模型摘要，只產生有來源與日期的草稿；使用者預覽接受後才更新紀錄，未知就標未知。

現有 [ROADMAP.md:26](ROADMAP.md:26) 已列出開始／結束工作 checkpoint 與記憶歷史，因此此方向是補完現有產品意圖，不是另起一套管理系統。該文件部分版本標題屬舊規劃，不能依其版號推定功能已交付。

## 7. 如何驗證有沒有真正解決痛點

### 使用情境

1. 專案很多：選三個近期投入的專案，重啟後仍保留選擇；其他專案隨時能搜尋到。
2. 久未接觸：挑三個至少兩週沒碰的真實專案，分別用舊流程與接續卡，觀察能否說清楚目的、停點及第一步。
3. 工作中斷：只用最小收工表單留下下一步，隔幾天回來檢查是否足以開始。
4. 沒有紀錄：舊專案無 checkpoint／無 Git 時，仍能補寫下一步，且沒有虛假的活動日期。
5. 有共享：確認聚焦偏好不外傳；收工內容若寫入原本共享欄位，界面有明確提示。

### 驗收目標，尚未測量

- 看接續卡後，目標一分鐘內知道第一個具體動作，不必先巡覽多個頁面。
- 最小收工記錄目標約 30 秒完成；能跳過，不成為新的管理負擔。
- 不要求清理全部舊專案才可開始使用。
- 不依賴 AI、登入或額外訂閱也能完成核心流程。
- 重開應用、並行編輯衝突、資料升級、Git 失敗均不丟失既有記憶。

### 實作時應補的測試

沿用現有 `tests/insights.test.ts`、`tests/db.test.ts`、`tests/device-storage.test.ts`、`tests/multi-group-devices.test.ts` 的基礎，增加：

- v4 升級後資料保留，新欄位為未知而非捏造日期。
- 聚焦／查看／啟動／輪詢不被當作工作完成，亦不干擾內容 revision。
- 快速收工保存的原子性、revision 衝突和失敗保留草稿。
- 個人欄位不出現在共享 DTO；既有共享欄位的語意不變。
- 暫停、封存、無 Git、空白下一步、舊快照、時區及時間邊界。
- 大量專案不產生逐卡 Git 查詢；Web 與 Electron 均有可用流程。

本輪僅研究，以上為未來驗證要求，不代表已執行或通過。
